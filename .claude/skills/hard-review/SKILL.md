# /hard-review

Ревью — второй по важности шаг после планирования: модели-исполнители часто халтурят (заглушки вместо логики, проглоченные ошибки, «TODO», тесты, которые ничего не проверяют). Работай на самой сильной модели.

## Шаги
1. **Область:** `git diff last-review` (тег прошлого ревью; если его нет — с первого коммита или с коммита, который назовёт пользователь) плюс `docs/SPEC.md` и `docs/PLAN.md`.
2. **Параллельные ревьюеры** (агент `code-auditor` или сабагенты), каждому одна тема и код, но не твои выводы:
   - корректность: баги, гонки, необработанные ошибки, краевые случаи;
   - демо: что сломает сквозной сценарий из SPEC (запусти и пройди его, для веба — агент `playtester`);
   - халтура: заглушки, захардкоженные ответы под видом AI, отключённые проверки, пустые тесты, `TODO`;
   - соответствие SPEC и кейсу: что заявлено, но не сделано;
   - безопасность: секреты в коде, открытые эндпоинты, которые тратят токены.
3. **Проверка находок:** каждую находку воспроизведи (тест, команда, шаги). Не воспроизводится — отбрось. Подтверждённые — таблицей: серьёзность, файл, как воспроизвести, как чинить.
4. **Починка:** с согласия пользователя чини по убыванию серьёзности, после каждой починки — проверка и коммит. Повтори шаг 2 только для изменённых файлов. В конце поставь `git tag -f last-review` — следующее ревью начнётся отсюда.

## Правила
- Без согласия ничего не переписывай целиком: точечные исправления.
- «Выглядит нормально» — не результат. Ревьюер, который ничего не нашёл, должен показать, что проверил.

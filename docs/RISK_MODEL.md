# Модель риска Qorgan

Источник истины — код `app/qorgan/risk.py` и `app/qorgan/policy.py`. Этот файл объясняет их для жюри и аналитиков.

## Принцип
Балл риска 0–100 — это **сумма именованных причин**. У каждого балла есть объяснение, которое видят клиент (простыми словами) и аналитик (с весом). Веса подобраны вручную как экспертные априорные значения для MVP. **Они не обучены и не откалиброваны на данных банка.** Калибровка — первая задача пилота (см. `docs/submission/INTEGRATION.md`).

Балл обрезается до диапазона 0–100.

## Уровни вмешательства

| Балл | Уровень | Что видит клиент |
|---|---|---|
| 0–29 | `allow` | ничего: перевод проходит сразу |
| 30–54 | `warn` | предупреждение с причинами, кнопки «Отменить» / «Всё равно перевести» |
| 55–100 или получатель похож на дроп | `safety_check` | проверочный диалог: «зачем вы переводите и кто попросил?» |

После проверочного диалога (`policy.decide_after_check`):
- ИИ распознал сценарий с уверенностью ≥ 0,6 → **задержка до решения специалиста** (закон с 01.01.2026 разрешает до 5 рабочих дней), кейс аналитику, уведомление доверенному лицу;
- получатель похож на дроп (`mule_pattern`: в стоп-листе / базе АФЦ или ≥ 30 баллов признаков дропа без учёта «новый получатель») → **задержка при любом ответе**: клиента могли научить, что сказать;
- балл ≥ 80 → **задержка** при любом ответе;
- иначе → клиент подтверждает перевод сам.

**Инвариант:** вердикт ИИ может только ужесточить решение. Снять задержку может только человек — аналитик. Это закреплено тестами `test_ai_cannot_release_a_high_score_transfer`, `test_ai_cannot_release_a_mule_transfer`, `test_coached_lie_to_a_mule_is_still_held` и `test_prompt_injection_cannot_whitewash_a_scam`.

## Почему правила, а не ML-модель в MVP
- Размеченных данных BCC у команды нет. Обучать модель на синтетических метках, которые мы сами придумали, значит выдавать собственные правила за «ML».
- Объяснимость обязательна: аналитик и регулятор должны видеть, почему перевод задержан.
- В пилоте эти признаки становятся фичами градиентного бустинга. Модель обучается на исторических инцидентах банка и АФЦ, а таблица причин остаётся объяснением (SHAP / вклад признаков).

## Дополнения после независимой проверки
- **Данные о получателе — только там, где банк их реально видит.** Возраст счёта, число отправителей за 24 ч и долю вывода BCC знает только по своим клиентам (core banking). Для получателя в другом банке эти поля пустые (`None`), и правила `young_account`, `fan_in`, `fast_cash_out` не срабатывают. Сигнал для другого банка — «серый» список АФЦ (`recipient_graylisted`, +25, сразу даёт `mule_pattern`). Межбанковый «индекс дропа» — наше предложение для пилота.
- **Дробление:** переводы тому же новому получателю за последние 24 ч суммируются (`split_transfers`, +15).
- **Крупно, непривычно, новому получателю, большая часть сбережений** (`new_recipient` + `amount_spike` + `drains_balance`) → всегда проверочный вопрос.
- **Давление** (звонок с незнакомого номера, сигнал оператора, удалённый доступ) → после вопроса перевод задерживается при любом ответе: клиент на линии с мошенником может повторить подсказанную легенду.
- **Удалённый доступ** → жёсткий блок перевода (требование регулятора, по данным СМИ).
- **«Вам сейчас кто-то говорит, что нажимать?» — «да»** → задержка. **Неоднозначный ответ** (`none` с уверенностью < 0,5, например «ok») → задержка.
- Деньги задержанного перевода **резервируются**, поэтому выпуск аналитиком не уводит баланс в минус.
